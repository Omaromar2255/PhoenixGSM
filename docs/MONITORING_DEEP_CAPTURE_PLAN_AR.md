## 1. 🔬 التشخيص الجذري المُثبت بالأدلة (لماذا تضيع الأوامر الآن؟)

### 📌 حقائق مؤكدة من فحص نظامك
| البند | الحالة |
|---|---|
| Secure Boot | ❌ معطّل (ممتاز لنا) |
| testsigning | ✅ مفعّل |

### ❌ المشكلة 1: بعض الأدوات لا يُلتقط لها أي أمر
**الأسباب الجذرية الثلاثة:**

1. **فلتر WMI ضيّق جداً** — في `MonitoringEngine.cs` السطر 135:
   الاستعلام يقبل فقط `TargetInstance.Name = 'adb.exe' OR 'fastboot.exe'`
   أي أداة تتكلم ADB **داخلياً عبر libusb/AdbWinApi/AdbWinUsbApi** (مثل UnlockTool الذي رأينا في مجلده `libusb-1.0.dll` و `AdbWinApi.dll` و `AdbWinUsbApi.dll`) **لا تُنشئ أي عملية adb.exe إطلاقاً** → WMI أعمى عنها تماماً.
2. **التقاط السيريال مستحيل بالطريقة الحالية** — `ComPortMonitor.cs` السطر 104 يستدعي `_port.Open()`، ومنافذ COM في ويندوز **حصرية**: إذا فتحتها الأداة (Z3X/Octoplus) لن نستطيع فتحها نحن، ويقع الاستثناء `UnauthorizedAccessException` (وهو ملتقط وصامت في السطر 120!) → **صفر التقاط دائماً** للبوكسات.
3. **الدرايفر مغطي فئة واحدة فقط** — فلتر `PhoenixUsbMonitor` مسجّل على `AndroidUsbDeviceClass` فقط. هاتف في وضع **Qualcomm EDL (9008)** أو **MTK Preloader/BROM** أو **مودم Samsung/Odin** يظهر كفئات أخرى (Ports / Modem / WinUSB-USBDevice) → الدرايفر لا يراه.
   ⚠️ ومخادعة أخطر: بطاقة الحالة تقول **"Active"** لأن جهاز التحكم `\\.\PhoenixUsbMonitor` يُنشأ في `DriverEntry` بغض النظر عن وجود أي هاتف ملتصق به الفلتر — أي أن "Active" لا يعني أننا نلتقط فعلاً!

### ❌ المشكلة 2: بعض الأدوات يُلتقط لها أمر واحد فقط
1. **ثقب WMI الزمني** — `WqlEventQuery("__InstanceCreationEvent", TimeSpan.FromSeconds(1), ...)` يعني `WITHIN 1 SECOND` = استطلاع كل ثانية. أي استدعاء `adb` قصير يبدأ وينتهي بين نبضتي استطلاع **يختفي بلا أثر** (أمر push/getprop سريع قد يعيش أقل من 200ms).
2. **معماريّة خادم ADB**: `adb.exe` مجرد عميل. العملية الأولى تشغّل **ADB Server طويل العمر** على TCP 127.0.0.1:5037، وكل الأوامر اللاحقة التي ترسلها الأداة تمر كبيانات داخل جلسة TCP موجودة أصلاً → **لا عمليات جديدة** → WMI لا يرى شيئاً بعد الأمر الأول.
3. `AdbInterceptor` الحالي (استبدال adb.exe) يسجل استدعاء البرنامج الخارجي فقط — وبعض الأدوات تشحن adb الخاص بها بمسار مختلف أو اسم معاد تسميته فلا تمر بالوسيط أصلاً.

### ❌ المشكلة 3: `adb shell` يُكتشف، وما بداخله لا يُكتشف
**هذا سلوك "طبيعي" للتصميم الحالي وليس خللاً عرضياً:**
- `adb shell` عملية واحدة → WMI يلتقطها ✅.
- كل أمر تكتبه بعد ذلك (`ls`, `getprop`, `pm`...) هو **بيانات خام داخل قناة ADB المفتوحة** (WRTE packets عبر USB نحو `shell:` service) — ليست عمليات ولا استدعاءات exe → WMI و Interceptor **عميان بنيوياً** عنها.
- الوحيد القادر على رؤيتها: **الدرايفر** (payload داخل WRTE) أو **اعتراض TCP 5037**.
- والمحلل الحالي به خلل إضافي: `AdbProtocolParser` يستخدم مخزنين عامين `_hostBuffer/_deviceBuffer` **مشتركين بين كل النقاط والأجهزة** — عند تداخل بيانات endpoints متعددة (ADB + Log + سيريال USB) يفسد إعادة التجميع وتضيع الحزم حتى لو وصلت من الدرايفر.

## 2. 🏗️ البناء المستهدف: "برج تحكّم خماسي الطبقات"

```
                ┌────────────────────────────────────────────┐
                │      Monitoring Studio (WPF) — العرض       │
                │  جلسات Shell معاد بناؤها + Hex/PCAP Export │
                └───────────────▲────────────────────────────┘
                                │ Phoenix Event Bus (قناة موحّدة
                                │  مرتبة زمنياً μs من كل الطبقات)
        ┌───────────┬───────────┼───────────┬────────────────┐
        │ L1        │ L2        │ L3        │ L4             │ L5
        │ ADB TCP   │ Process   │ USB       │ Serial Kernel  │ API
        │ MITM 5037 │ Trace     │ Driver    │ Filter (Ports) │ Hook
        │ (Pure C#) │ (ETW/WMI  │ (محسّن +  │ يلتقط UART دون │ (اختياري
        │           │ إجباري)   │ متعدد     │ فتح المنفذ    │  للعنيدة)
        │           │           │ الفئات)   │                │
        └───────────┴───────────┴───────────┴────────────────┘
```

### 🔷 L1 — بروكسي ADB الشفاف على المنفذ 5037 (**قلب الحل**)
**الفكرة:** نسيطر على المنفذ القياسي 5037 الذي يتحدث إليه *كل* عميل ADB في الجهاز (CMD، أدوات الصيانة، مكتبات AdbWinApi...).
- نشغّل خادم ADB الحقيقي على منفذ داخلي (مثلاً 5038: `adb -P 5038 nodaemon server`)
- بروكسي Phoenix يستمع على **5037**، ويمرر البيانات بايت-بايت بين العميل والخادم الحقيقي، مع تفكيك بروتوكول ADB أثناء المرور:
  - **Smart-Socket framing**: `هوست:خدمة` بصيغة `4 أحرف hex طول + payload` → نستخرج اسم الخدمة كاملاً (`shell:ls -la`, `exec:`, `sync:`, `host:track-devices`...)
  - **بعد المصافحة**: البيانات تتحول لحزم ADB الخام (CNXN/OPEN/WRTE/CLSE) → نغذيها لنفس `AdbProtocolParser` الموجود
  - **أوامر الشِل التفاعلية**: payload لكل WRTE داخل stream معرف بـ `(arg0,arg1)` → **مُجمّع جلسات Shell** (لكل stream نص طرفية متكامل: ما كتبه المستخدم + رد الهاتف)
- **Fail-Open Watchdog**: لو مات البروكسي → watchdog يعيد الخادم الحقيقي لـ5037 خلال <500ms حتى **لا تنكسر أي أداة** أبداً.
- **يحل:** المشكلة 3 كاملةً + المشكلة 2 لأدوات ADB + يلتقط حتى `UnlockTool/libusb` إن استخدم عميل ADB قياسي.
- بدائل مرفوضة مع سبب: مراقبة ETW للشبكة (لا payload) · Npcap loopback (أداة طرف ثالث + سلبي فقط) · إبقاء استبدال adb.exe (يغطي مساراً واحداً فقط).

### 🔷 L2 — التقاط العمليات بمعدل نجاح 100%
| التقنية | ما تضيفه |
|---|---|
| `Win32_ProcessStartTrace` (WMI event-driven حقيقي، بلا WITHIN) | زمن استجابة فوري، **لا يفوّت العمليات القصيرة** (يحل المشكلة 2 سبب#1) |
| ETW `Microsoft-Windows-Kernel-Process` عبر مكتبة TraceEvent | يعطي **CommandLine كامل** + ضمان kernel-level · بديل أقوى |
| موسّع المطابقة | أي عملية ابنة لأداة GSM معروفة + أي exe يحمل اسم `*adb*`/`*fastboot*` + **كشف المعاد تسميته** عبر `FileVersionInfo.OriginalFilename == "adb.exe"` |
| بناء شجرة عمليات لكل أداة | ربط كل أمر لاحق بالأداة الأم في التقرير |

### 🔷 L3 — تعزيز درايفر USB الحالي (4 إصلاحات + توسعة)
1. **الالتصاق الفعلي بالجهاز:** بعد تسجيل UpperFilters → إجبار إعادة بناء المكدس فور توصيل الهاتف (`pnputil /restart-device`) أو عبر `CM_Reenumerate_DevNode` من DriverManager — وتصحيح بطاقة الحالة: IOCTL جديد `IOCTL_PHX_GET_ATTACH_COUNT` يُظهر "Active on N device(s)" بدل الوهم الحالي.
2. **قناة سحب بلا فقد:** رفع Ring Buffer (512→8192) + عدّاد إسقاط يظهر في الواجهة + استبدال `Task.Delay(10)` بانتظار Event من الدرايفر (event-driven dequeue).
3. **إصلاح المُحلل:** إعادة تجميع keyed لكل `(DevicePath, Endpoint, Direction)` بدل مخزنين عامين + خيوط reconstruction لكل ADB stream.
4. **توسيع التغطية لأنماط الصيانة** (DeviceLowerFilters مستهدفة بالـ VID/PID — لا نلمس فئات عامة):
   | النمط | VID:PID شائعة | البروتوكول |
   |---|---|---|
   | QC EDL | 05C6:9008 | Sahara/Firehose |
   | MTK | 0E8D:0003/2000/6000 | Brom/Preloader/DA |
   | Spreadtrum | 1782:4D00 | BOOTROM/FDL |
   | Samsung DL | 04E8:685D/6601 | Odin/Thor |
   | Fastboot | 18D1:D00D + كل المصنّعين | Fastboot |
   | CDC/Serial مجسّات | ftdi 0403، CH340 1A86، PL2303 067B | UART-over-USB |
   + مُفككو بروتوكولات: Fastboot · Sahara(QPY) · Firehose(XML) · MTK-DA · Thor · DIAG-HDLC(7E + CRC16).

### 🔷 L4 — فلتر السيريال النووي (يحل البوكسات نهائياً)
- **UpperFilter صغير على فئة Ports** `{4D36E978-E325-11CE-BFC1-08002BE10318}` (نفس .sys كوضع ثانٍ): يعترض `IRP_MJ_WRITE/READ` على serial devices → يرى **كل ما ترسله وتستقبله Z3X/Octoplus دون فتح المنفذ إطلاقاً** — لا تعارض، لا UnauthorizedAccess.
- مُفكك مدمج: AT commands · QC DIAG (HDLC 0x7E framing, CRC-16-CCITT, escape 0x7D) · Samsung GSM/ODM.
- حصر الالتصاق بأجهزة USB-Serial المعروفة (VID محددة) لتجنب لمس مودمات النظام.

### 🔷 L5 — (اختياري، للأدوات العنيدة 1%)
حقن DLL خفيف (MinHook) داخل عملية الأداة عند رصدها → hooks على `WinUsb_WritePipe/ReadPipe` + `libusb_bulk_transfer/control_transfer` + `WriteFile/ReadFile` على COM → بث للـ Event Bus. **لا نحتاجه إن عملت L3/L4** — نبنيه فقط إن ثبتت أداة مُحددة تفلت.

| المرحلة | المحتوى | المكسب الفوري | مخاطرة | معيار القبول |
|---|---|---|---|---|
| **P0 — إصلاحات سريعة** (نصف يوم) | L2 كامل + عدّاد إسقاط + restartedevice + تصحيح بطاقة الحالة | التقاط كل استدعاءات adb/fastboot بلا فقد | منعدمة | 20 استدعاء adb سريعاً → 20 مسجلاً |
| **P1 — بروكسي 5037** (3-4 أيام عمل مركّز) | L1 كامل + مجمّع جلسات Shell + Fail-Open | **أوامر داخل adb shell + كل عمليات UnlockTool/SamFW النوع ADB تظهر كاملة** | منخفضة (كسر الأدوات منفياً بالـ Watchdog) | جلسة `adb shell` تفاعلية = transcript نصي كامل متطابق مع الطرفية |
| **P2 — الدرايفر متعدد الأنماط** (3-4 أيام) | L3 (الإصلاحات + VID/PID filters + Firehose/Sahara/Fastboot parsers) | EDL/MTK/Odin مغطاة + PCB-level مضمون | متوسطة (اختبار driver verifier) | فلاش Firehose على جهاز QC يظهر XML كاملاً |
| **P3 — فلتر Ports** (يومان) | L4 + AT/DIAG parsers | Z3X/Octopus على COM تُقرأ أخيراً | متوسطة | عملية Read Info على Z3X → AT commands مرئية live |
| **P4 — لمسات الأسد** (اختياري) | PCAP/Wireshark export · رسوم Timeline · بحث IMEI ذكي · بثّ عبر localhost لأدواتك الأخرى | تحليل احترافي ومشاركة | منعدمة | ملف .pcap يُفتح بنجاح في Wireshark |

> **توصية البدء: P1 أولاً** — أكبر عائد (يحل شكواك 2 و3 بالكامل) بلمسة C# خالصة بلا مخاطر كيرنل، وP0 يُدمج معها كيوم تحضيري.

## 4. 🧪 سيناريوهات الاختبار الإلزامية (قبل اعتماد أي مرحلة)
1. **شِل تفاعلي:** `adb shell` ثم 15 أمراً يدوياً → كلها تظهر بنصّها ورد الهاتف، ms-delta < 50.
2. **سيل قصير:** سكربت 50× `adb shell getprop x` متتالية → 50/50 مسجلة (يختبر ثقب WMI).
3. **UnlockTool FRP** على Motorola موصول ← transcript ADB كامل + اللحظات الزمنية.
4. **fastboot flash** (fastboot.exe) من كونسول خارجي ← WRTE/BULK مُفكك.
5. **Z3X على COM** ← أوامر Box مرئية والمنفذ يظل يعمل طبيعياً للأداة (لا تعارض).
6. **فصل/وصل الهاتف** ×5 ← الفلتر يعيد الالتصاق ذاتياً والعداد يؤكد `attached=1`.
7. **قتل البروكسي قسراً** (taskkill) ← الأدوات تكمل العمل خلال <1s (Fail-Open حي).

## 6. ❓ قرارات مطلوبة منك قبل أي سطر كود
1. **نقطة البدء:** نوصي P1 (بروكسي 5037 + مجمّع الشل) — موافق أم تفضّل ترتيباً آخر؟
2. **نطاق L3:** فلاتر VID/PID مستهدفة (آمن) أم فلتر شامل على Hub يرى كل USB حتى لوحة المفاتيح (مفرط — لا ننصح به)؟
3. **L5 (حقن API):** نبنيه الآن ضمن الخطة أم مؤجل حتى تثبت أداة فالتة فعلاً؟
4. **مصير AdbInterceptor الحالي** (adb_real.exe في UnlockTool): نعيد adb الأصلي بعد P1 (الأنظف) أم نبقيه كطبقة تكميلية؟
